# Findings: `@docstack/react` 0.0.9 / `@docstack/client` 0.1.6

Written 2026-08-26, from `paper` at `@docstack/react@0.0.9` and `@docstack/client@0.1.6`
(local build). Both findings are reproducible from
[`packages/web/tests/app-boot.spec.ts`](../../packages/web/tests/app-boot.spec.ts) —
`npm run test:e2e`, no credentials needed.

---

## 1. `StackProvider` races itself when its effect runs twice — `409 Document update conflict`

**Severity:** high. Every load under React StrictMode; intermittently without it.

### What happens

```
DocStack provider - failed to reconcile stacks
Error: {"status":409,"name":"conflict","message":"Document update conflict"}
    at ClientStack.applyPatches
    at async ClientStack.checkSystem
    at async ClientStack.initdb
    at async ClientStack.create
    at async DocStack.addStack
```

The patch that collides is the system one, `~sys-0.0.1`.

### Why

In `lib/components/StackProvider/index.js`, the effect has two branches:

```js
if (docStackRef.current === null) {
    const instance = new DocStack(...mergedConfig);
    docStackRef.current = instance;
    instance.addEventListener("ready", setsDocStackWhenReady);
    // ...
    return;                     // <- registers no cleanup, and returns nothing to await
}
// ...otherwise reconcile
reconciling.current = reconciling.current.then(reconcile)
```

The constructor opens the configured stacks **asynchronously**. The `reconciling` promise
chain — which exists precisely so that "two overlapping passes would race to add the same
stack twice", per its own comment — is only ever joined by the *second* branch. The
constructor's own in-flight work is not in the chain.

So on a second effect pass that lands before the constructor has finished:

1. `docStackRef.current` is non-null, so the reconcile branch runs.
2. `instance.getStack('paper-stack')` is still `undefined` — creation is in flight.
3. It concludes the stack is missing and calls `instance.addStack(cfg)`.
4. Two `initdb` → `checkSystem` → `applyPatches` runs write `~sys-0.0.1` concurrently.

StrictMode guarantees that second pass in development. Outside StrictMode any change to
the effect's dependencies during startup does the same — and `mergedConfig` is rebuilt from
`JSON.stringify(config)`, so an application whose config identity moves early is exposed.

Confirmed by removing `React.StrictMode`: the 409 disappears, everything else is unchanged.

### Suggested fix

Put the constructor's initialisation into the same queue everything else waits on:

```js
if (docStackRef.current === null) {
    const instance = new DocStack(...mergedConfig);
    docStackRef.current = instance;
    instance.addEventListener("ready", setsDocStackWhenReady);
    instance.addEventListener("stack-added", signalStacksChanged);
    instance.addEventListener("stack-removed", signalStacksChanged);
    // The constructor opens the configured stacks asynchronously. Until that settles,
    // `getStack()` answers `undefined` for a stack that is already being created, so a
    // reconcile pass in that window adds it a second time.
    reconciling.current = reconciling.current.then(
        () => new Promise(resolve => instance.addEventListener("ready", () => resolve(), { once: true })),
    );
    return;
}
```

Worth having as well, as defence in depth: make `DocStack.addStack` reject or no-op for a
name whose creation is already in flight, rather than relying on callers to check
`getStack()` — the check is not atomic across an `await`.

## 2. Hooks report a missing provider during the normal pre-ready window

**Severity:** low, but noisy and misleading.

`lib/hooks/class.js` (and the same shape in the other hooks):

```js
useEffect(() => {
    if (!docStack) {
        console.error('useClass must be used within a DocStackProvider.');
        setLoading(false);
        return;
    }
```

`StackProvider` publishes `null` into the context until its `ready` event fires, so this
runs on every load with the provider correctly in place. Two problems:

- The message is wrong, and sends the reader looking for a missing provider.
- `setLoading(false)` is worse than the log. A consumer distinguishing "loading" from
  "loaded, empty" is told the data is loaded and absent, during startup — which is a real
  correctness trap, not just noise.

### Suggested fix

Distinguish "no provider" from "provider not ready". The context could hold a sentinel
rather than `null` so the two are separable — but even without that:

```js
if (!docStack) {
    // The provider publishes null until `ready`; that is startup, not a missing provider.
    setLoading(true);
    return;
}
```

...and warn only if it is still null after some grace period, or drop the warning
entirely in favour of documenting that hooks return `loading` until the stack opens.
