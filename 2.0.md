# DocStack 2.0 — what the release is

Status: proposed · Date: 2026-11-15 · Scope: every published `@docstack/*` package, the
android modules, the new Rust core

Two proposals land at once and point the same way: `proposal.md` moves the data model
into code, `ports.md` moves the engine into Rust. Together they change the public
surface enough that the next release is a major one, so it is named here and planned as
one release. This document owns the release: what 2.0 is, what it breaks, what ships
when, and how versions are cut. Design detail stays in the two proposals.

**For the IDE agent.** This file is a direction, not a work order. Nothing here
authorises code beyond the spikes gated in `ports.md` §9. Items marked **VERIFY** or
**Open** were not settled while drafting.

---

## 1. The three decisions 2.0 records

1. **The model is code.** A class is declared in the app's source, its TypeScript types
   are inferred from that declaration with no codegen step, and patches are generated
   from the diff against the folded patch chain (`proposal.md`). The untyped runtime
   API stays as an escape hatch.
2. **The engine is Rust, behind an unchanged surface.** One core compiled per target:
   Wasm and a napi addon for JS, generated bindings for Kotlin, C# and Swift
   (`ports.md`). Storage and remotes stay pluggable in the host's own language.
3. **A port is a compiled binding, never an embedded JS engine.** The embedded-JS track
   (`android/docstack-headless`, QuickJS via Zipline) is dropped rather than kept as a
   fallback — §4.

## 2. Contract first: 2.0 is not hostage to the spikes

The Rust core sits behind `ports.md` §9's go/no-go spikes, and S1 (rev-tree merge) and
S2 (replication interop) can still fail. The release is therefore defined by **the
public contract, not the implementation**:

- **2.0.0 ships the contract** — model-first typed authoring, explicit backend
  selection, the compiled/runtime handler split, PouchDB demoted to an optional peer —
  running on today's TypeScript engine. Every breaking change a consumer sees happens
  here, once.
- **2.x swaps the implementation** — the Rust core takes over the JS package's internals
  behind that same surface (`ports.md` §10 phase 4), then the native bindings arrive.
  A new platform is a new package, not a new major.

If S1 or S2 fails: 2.0 has already shipped, JS stays on PouchDB, and the native ports do
not happen (§4 leaves no fallback, deliberately). Nothing has to be unshipped.

## 3. What 2.0 breaks

| Change | Today | 2.0 | Detail |
|---|---|---|---|
| Backend is explicit | `StackOptions` extends `PouchDB.Configuration.DatabaseConfiguration` and unknown keys pass through to the constructor (`client/src/core/stack.ts`, `toPouchConfiguration`) | `backend:` selects the built-in engine or a PouchDB instance | `ports.md` §4.1 |
| PouchDB dependency | required by `@docstack/client` | optional peer dependency; only PouchDB users install it | `ports.md` §4.1 |
| Runtime string triggers and jobs | `TriggerModel.run` / `PatchJob.content` evaluated by the client | need the optional runtime plugin; without it, writes to an affected class are **refused** and runtime jobs stay pending | `ports.md` §5.3 |
| Handler references | source strings only | optional `handler?: string` on `TriggerModel` and `PatchJob`; exactly one of `handler` / `run` (or `content`) | `proposal.md` §13 |
| Model authoring | untyped JSON inside patches | `defineClass`, generated patches, `revision --check` in CI | `proposal.md` §6 |
| `integer` accepts decimals | `z.number()` with no `.int()` | **landed**: `.int()`, which rejects decimals already stored | `proposal.md` §8 defect 3 |
| `enum` values | config allows `string \| number \| object`, runtime `z.enum` takes strings only | **landed**: strings only, and a non-string raises a named error | `proposal.md` §8 defect 2 |
| `date` attribute type | declared in `shared/src/types.ts`, throws at `setField` | **landed**: an ISO-8601 UTC string, `format: "date"` for date-only | `proposal.md` §8 defect 1 |
| Embedded-JS ports | `docstack-headless` in development | dropped | §4 |

The data-shape rows are the argument for doing this as a major: `integer` and `enum` are
breaking for data already on disk, `date` changes a declared type, and 2.0 is the only
window that does not need a migration story bolted onto a minor release.

## 4. The embedded-JS port track is dropped

**Decision.** `android/docstack-headless` (the QuickJS/Zipline carrier) stops
development at 2.0. It is not an interim step toward the Rust core, and it is not the
fallback if the core fails.

Why:

- **It fails the first goal of `ports.md`.** Every port would ship a JS engine, and the
  WASM-less engines (QuickJS, Jint) cannot run `@docstack/abe`, so cryptographic access
  (ADR-0045) is missing exactly where the port promised parity.
- **It runs today only against a patched Zipline.** Two real bugs were root-caused and
  fixed in a local clone and PR'd upstream (cashapp/zipline#1833); the module is pinned
  to that build through `mavenLocal()` and a `1.28.0-SNAPSHOT` version
  (`android/docstack-headless/SPIKE-NOTES.md`, "Real module", resolved 2026-08-11).
  Carrying a fork of the host's JS runtime is a standing cost for a path we intend to
  replace.
- **It keeps two engines alive for years**, which is the thing `ports.md` goal 3 exists
  to prevent.

What this does **not** drop:

- `android/docstack-store` (Kotlin, RocksDB) — kept, and becomes a foreign
  `DocumentStore` for the core (`ports.md` §3.2, §7). Its spec-02 semantics carry over.
- `android/docstack-permetic` and `@docstack/pouchdb-adapter-native` — kept, in the plan,
  and not deprecated. A web app in a Permetic WebView runs the real JS client over the
  native store, which is the topology android specs 01, 03 and 05 describe. What changes
  is that **Permetic is not the route to native hosts**: nothing new is built on it to
  serve a plain Kotlin or JVM app, because one Rust-built Kotlin/JVM library is expected
  to cost less than extending a WebView carrier to do the same job (decided 2026-11-15).
- The optional **runtime-handler plugin**, which may embed QuickJS on native hosts
  (`ports.md` §5.2). Sandboxing an interpreter for end-user handler code is a different
  thing from running the engine in JS: it carries no engine logic, it is optional, and
  an app that omits it cannot execute runtime handlers at all.

**Consequence, decided 2026-11-15.** `android/ROADMAP.md` targeted a plain Kotlin app on
`docstack-store` + `docstack-headless` in primary-carrier mode. That app **waits for the
Kotlin binding** (`ports.md` §10 phase 5) rather than shipping on the Permetic WebView
carrier, so it holds until the core lands. Two things follow:

- Its phases 3 and 4 are cancelled, not paused, and `android/specs/04` is superseded.
  The android plan documents carry this (`android/ROADMAP.md`, `android/CLAUDE.md`,
  `android/specs/04`, `android/specs/05`, `android/specs/02` D-1, ADR-0002's amendment).
  The submodules themselves were not touched.
- **S6 now gates a product**, not just the order the native languages ship in, so the
  Kotlin binding moves ahead of the server in §6. Phases 0–2 of that roadmap keep their
  value: `docstack-store` becomes a foreign `DocumentStore` (`ports.md` §3.2) and the
  adapter's vendored PouchDB suite becomes the store conformance suite (`ports.md` §8).

## 5. Versions

- Every published package goes to **2.0.0 together** and moves as one line afterwards,
  so an app can pin `2.x` across `client`, `react`, `shared`, `server` and the adapters.
  They drift independently today: `client` 0.3.2, `react` 0.1.3, `shared` 0.1.1, `abe`
  0.1.1, `server` 0.1.0 (unpublished).
- `@docstack/cli` and `create-docstack` (`proposal.md` §12) start at 2.0.0 to match.
- **Open:** cut today's `main` as **1.0.0** first, giving a supported line to bugfix
  while 2.0 is built, or leave the shipped line on 0.3.x so 2.0.0 is simply the first
  major. Recommended: cut 1.0.0 — the repo has no tags, and the client's `Unreleased`
  changelog section already holds engine sessions (ADR-0046) and the server work
  (ADR-0047), which is a release in its own right.
- A 1.x → 2.0 **migration guide is a release deliverable**: the backend option, the
  handler split, the data-shape fixes in §3, and replicating a PouchDB-backed stack
  into the built-in engine (`ports.md` §3.1).

## 6. Order of work

| Release | Contents | Gate |
|---|---|---|
| 2.0.0 | `proposal.md` phases 1–6 (typed model, fold/diff, CLI, typed client and react surfaces, docs) and `ports.md` §10 phase 1 (handler layers, runtime extracted as an optional plugin, fail-closed), both on the TS engine; the §3 data-shape fixes; the migration guide | S9 on the TS client |
| 2.1 | Rust core behind the JS package: engine, built-in stores, replicator, backends ①②③ | S1–S5, S7 |
| 2.1–2.2 | **Kotlin/JVM binding** with `docstack-store` as a foreign store | S6 |
| 2.2+ | `@docstack/server` on the napi addon with the Postgres store | S8 |
| later | C#, then Swift | S6 |

The Kotlin/JVM binding sits ahead of the server because `android/ROADMAP.md`'s app is
held for it (§4). It needs the core's own phases complete (`ports.md` §10 phases 2–3)
plus S6, and ships as soon as both are true — it does not wait for the JS package's
internals to be switched over. One UniFFI binding serves Android and plain JVM, which is
the reason this path is expected to cost less than the carrier it replaces. The server's
gate (S8) is independent, and nothing the android app needs depends on it;
`@docstack/server` keeps running on `pouchdb-node` until then.

Numbers past 2.0.0 are sequence, not dates. `ports.md` §10 owns the phase detail and
`ports.md` §9 owns the gates.
